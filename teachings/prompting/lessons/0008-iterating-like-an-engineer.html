Iterating like an engineer — evals & the prompt debug loop

The meta-skill that makes the other seven compound: stop judging prompts by vibes, and start measuring them.

The one win You can turn "did this change help?" from a gut feeling into a measured yes/no — a tiny eval plus a one-variable-at-a-time debug loop.

The problem with "that looks better"

Everything you've learned so far — explicit intent, altitude, examples, effort, verification — is a change you make to a prompt, a skill, or a CLAUDE.md rule. And every change raises the same question: did it actually help, or did you just get a good roll? Judging one output by feel can't answer that. The model is stochastic: the same prompt gives different runs, so a single nice result is evidence of almost nothing. This is the discipline that ties the whole course together — treat prompt work like engineering, not vibes.

An eval is small, concrete, and checkable

An eval is a handful of representative test cases — inputs — each paired with a checkable pass condition: an expected property, or a rubric you can score against. Five to ten cases beats judging one output by feel, every time. And — straight from Lesson 4 — the cases must be representative, which means including the hard ones: the weird provider, the empty input, the cassette that should be rejected. An eval of only happy paths certifies only the happy path.

For your work that's concrete. Testing a skill or a CLAUDE.md rule? Your eval is a set of representative cases — a normal EVM chain, a non-EVM protocol, a provider with a custom method, a malformed cassette. Each case has a bar: schema regenerates, type-checker passes, CU mapping present, no rule violated. That set is your instrument.

Define the bar first

Before you touch anything, write down what "good" means — the same "define done" move from Lesson 6. Without a bar you cannot tell improvement from noise; you'll stare at two outputs, prefer whichever you read second, and call it progress. Decide the pass condition first, while you're honest, then let the runs fall where they fall.

The loop: change one thing, run, compare, keep or revert

Then it's classic debugging. Change one variable — the wording, one example, the effort tier, a single rule. Run the eval. Compare to the bar. Keep the change or revert it. Change two things at once and you cannot attribute the result to either; that's not iteration, that's guessing with extra steps.

Because the model is stochastic, "it passed once" is not a pass. Run each case a few times and judge consistency — a fix that works on one roll and fails on the next hasn't fixed anything. The goal isn't one green run; it's a process you trust.

Vibes

"I reworded the add-chain skill and the next run looked cleaner, so it's better — shipped." One run, no bar, two edits bundled in. You can't say what helped, or whether the next run regresses.

Measured

"Five representative chain cases, bar defined up front. Changed only the wording, ran each three times, compared to the bar. Four of five improved and held across runs — kept it; the effort bump is a separate run."

This is how you ran the sweep

You've already met this loop without the name. The effort sweep from Lesson 6 — running across effort tiers against "your own eval set" — is this process, with effort as the one variable. Refining the sharpen skill is the same loop with wording as the variable. Knowing a CLAUDE.md change actually helped is the same loop with the rule as the variable. One method, everything downstream.

Keep the eval set as a regression suite: re-run it whenever you change the prompt, the skill, or the model. That last one matters — models change (the migration Lesson 5 covered), and a suite that certified the old model is exactly what tells you whether the new one still clears the bar.

When judging doesn't scale, judge with the model

When hand-judging doesn't scale, scale it with the model: an LLM-as-judge scores outputs against a rubric. But the judge needs a clear rubric — show-don't-tell applies to the judge too, and a vague rubric produces vague scores. Independent or adversarial judges raise confidence, the same verification instinct as Lesson 7.

Sharp beats big A tiny, sharp eval with a real bar beats a big, vague one — five cases you can actually check are worth more than fifty you eyeball. And say it once more, because it's the trap everyone falls into: a single passing run is not verification. Consistency across runs is.

Check yourself

Why isn't one passing run proof that a prompt change helped?

Why change only one variable per run in the debug loop?

Do it once

You just tweaked a skill or a CLAUDE.md rule — say you loosened a rule in the add-chain skill so it stops over-editing the OpenAPI schema. Right now you'd judge it by running it once and eyeballing the diff. Instead: sketch a 5-case eval and the one-variable loop you'd run. Name the cases, the bar, what single variable you change, and how you decide keep-or-revert.

Model answer

The bar, first. A run passes when: the type-checker is green, the OpenAPI schema regenerates with no unintended edits, CU mappings exist for the new methods, and no explicit CLAUDE.md rule is violated. Written down before I touch the skill.

Five representative cases (deliberately not all happy): (1) a plain EVM chain; (2) a non-EVM protocol with custom JSON-RPC methods; (3) a provider that already exists, so no schema churn is expected; (4) a chain whose config is subtly malformed and should be rejected; (5) a chain that previously triggered the over-editing bug — the case this change exists for.

The loop. Change exactly one variable: the loosened rule wording — nothing else, not the effort tier, not the examples. Run all five cases three times each (stochastic, so I judge consistency, not a single roll). Compare each run to the bar. Keep only if the target case (5) now clears the bar and cases 1–4 still hold across runs — no regressions. If case 3 starts churning the schema or case 4 stops rejecting, I revert and try a narrower wording. Then this five-case set becomes the regression suite I re-run next time I touch the skill, or when the model changes.
