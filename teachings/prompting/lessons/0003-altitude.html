Prompting · Lesson 3 · Altitude

Altitude

How much to specify — and why CRITICAL: YOU MUST makes a capable model worse.

Lessons 1 and 2 were about adding the right things: explicitness, intent, a decision frame. This one is about the opposite failure — adding too much, or adding it too loud. Altitude is the level of abstraction you hand off at: do you tell the model the outcome and let it find the method, or do you dictate every step? Get the altitude wrong and even a perfectly explicit prompt underperforms.

The one win You'll know when to stop specifying — and you'll delete the ALWAYS / NEVER / CRITICAL shouting from your skills, because on Opus and Fable it actively hurts.

Altitude = the level you hand off at

Picture a spectrum. At low altitude you dictate method: "run npm test, read each line, if a test fails fix it, re-run…" At high altitude you state the outcome: "make sure your change doesn't break the suite before moving on." Neither is universally right — the skill is choosing deliberately.

The default that works most of the time: constrain the outcome and the boundaries; leave the method to the model. Drop to lower altitude only where the method is load-bearing — a specific helper it must use, an order that actually matters, a trap to avoid.

Too low (micromanaged)

"First open the file. Then find the function. Then read the whole thing. Then change line 12. Then save. Then check it compiles. Then…"

Right altitude

"Fix the off-by-one in paginate() in list.ts — it drops the last page. Use the existing clampPage() helper rather than a new guard. Don't change the function's signature."

The good version is high altitude on method (it doesn't narrate the edit) but drops low on the two things that are load-bearing: use clampPage() and don't change the signature. That's the move — altitude isn't one setting for the whole prompt, it's per-decision.

Volume is not clarity — delete the shouting

Here's the counterintuitive part, and it's specific to current models. Prompts full of CRITICAL: YOU MUST ALWAYS… were written to overcome older models that ignored instructions. Opus 4.8 and Fable have the opposite problem: they follow instructions literally and eagerly. Shouting at them doesn't add reliability — it makes them over-trigger: reaching for a tool when they shouldn't, refusing to use judgment, over-engineering a simple ask.

Straight from Anthropic's model guidance The migration guidance for Opus 4.7/4.8 says it plainly: rewrite CRITICAL: You MUST use this tool when… → Use this tool when…, and delete If in doubt, use [tool] entirely — it now overtriggers. For Fable it's stronger still: prompts written for older models are "often too prescriptive and reduce output quality." The fix is to state the rule once, plainly, with the why (Lesson 1) — not to escalate the volume.
Source: in-repo claude-api skill · Model Migration guidance.

Loud (backfires)

"CRITICAL: You MUST ALWAYS write tests. NEVER EVER skip this. This is NON-NEGOTIABLE."

Once, plainly, with the why

"Write tests for new behavior — this repo ships from main, so untested code goes straight to production. If something genuinely can't be tested, say so and why."

Match the altitude to the model

Altitude isn't absolute — it depends who's reading. A more capable model wants a higher altitude, because its own planning is good and over-prescription gets in its way.

ModelPrompt at…Because
Fable / Opus 4.8 High altitude: goal + constraints + the why. Trust its planning. Over-prescription measurably lowers Fable's output quality; it plans well on its own.
Smaller / older models Lower altitude: more explicit steps, worked examples. Less able to bridge from goal to method; the scaffolding does real work.

This is why the same skill can feel over-engineered on one model and under-specified on another. When you upgrade the model behind a skill, re-read the prompt and raise its altitude — strip the step-by-step and the shouting you added for the weaker model.

Altitude, in one line Specify the outcome and the load-bearing constraints; leave everything else to the model; say each thing once, plainly. The stronger the model, the higher you fly.

Do it once

Here's a real-shaped over-prescribed, over-loud CLAUDE.md rule. Rewrite it: raise the altitude, drop the volume, keep only the load-bearing bits. Then reveal.

"CRITICAL: You MUST ALWAYS run the full test suite after EVERY single
change. First run `npm test`. Then read the output line by line. Then
if ANY test fails you MUST fix it before doing ANYTHING else. Then
re-run `npm test` AGAIN to confirm. NEVER skip any of these steps."
Reveal one strong rewrite (compare the moves)

"After a change, make sure the test suite is green before moving on — this repo ships from main, so red means broken production. Use your judgment for changes too small to have tests."

The moves: altitude raised (outcome "suite is green," not the run/read/fix/re-run choreography — the model already knows how to run tests) · volume dropped (no caps; stated once) · the why kept (ships from main → Lesson 1) · judgment restored (the loud version forbade it; the model over-applying "test everything" to a one-line rename is exactly the over-triggering this lesson warns about).

The trap on the other side "Raise the altitude" is not "say less." Fly too high and you're back to Lesson 1's under-specification — the model fills gaps with defaults you didn't want. The target is precise about outcomes and boundaries, quiet about method. Vague-and-quiet fails just as hard as loud-and-micromanaged.
