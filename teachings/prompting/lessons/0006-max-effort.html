Prompting · Lesson 6 · Effort

Max effort — the top of the dial

How hard the model thinks per step — and why the top setting is usually the wrong reach.

The one win You can pick an effort level on purpose — and you know why max is almost never the answer.

The dial

Effort runs low → medium → high → xhigh → max. One dial, two coupled things: how deeply the model thinks per step and how many tokens it spends doing it. Turn it down and you get fewer, more-consolidated tool calls, less preamble, terser confirmations. Turn it up and you get more deliberation before it acts.

This all happens inside one agent, one context — it is not fan-out, not subagents, not a bigger model. It is a single Claude instance thinking harder or less hard at each turn. In the API you set it with output_config.effort; in Claude Code it is a session setting. The default is high (the same as omitting it). xhigh sits between high and max and is the default in Claude Code — the sweet spot for most coding and agentic work.

Not the same as speed Fast mode is a separate API research preview (speed: "fast", on Opus 4.8/4.7) that raises the output tokens-per-second rate. It is orthogonal to effort: it changes how fast the tokens come out, not how hard the model thinks. Speed and effort are two different dials — don't conflate them.

Two halves of "how much"

Lesson 3 was about altitude: how much you specify — the height you pitch the instruction at. Effort is the other half: how much the model thinks about what you gave it. Altitude is your work; effort is its work. They multiply. A low-altitude, vague ask at max effort just buys you expensive deliberation over an underspecified target — the model spends tokens guessing at the spec you didn't write. This tension also showed up in Lesson 5, where lower effort on Fable already cleared older models' ceilings.

What max is actually for

max is for the rare case where correctness matters more than cost: an extremely hard, latency-insensitive task where you'd happily pay for every extra unit of thinking. That's the whole brief. Reach for it when a wrong answer is expensive and you have time to wait.

Its failure mode is the flip side: diminishing returns and overthinking. Past a point, more tokens stop buying more correctness — the model deliberates over decisions that were already settled, second-guesses good first passes, and burns budget without moving the outcome. Reaching for max reflexively costs you money and latency for gains you often can't measure.

Reflexive max

"Important refactor across the request-router — set effort to max so it's definitely right." You pay top-of-dial latency and tokens on a task high or xhigh would have nailed, and risk overthinking a clean change.

Deliberate pick

"This is a normal agentic change — start at xhigh (CC's default). If a genuinely hard, correctness-critical migration comes up and I can wait, I'll bump to max for that run only."

The discipline: sweep, don't assume

The intelligence / latency / cost relationship is not monotonic. Higher effort up front often reduces total cost on agentic work — deeper first-pass thinking means fewer wasted turns, so the whole task finishes in less back-and-forth. For other tasks, medium is just as good and faster. You cannot reason your way to the right tier from the armchair.

So sweep it. On Opus 4.8, start at high and iterate — run medium / high / xhigh against your own eval set and read the numbers. On Fable 5, low effort already performs very well, often beating older models at xhigh or max; if a task completes correctly but slowly, turn the dial down. Reserve max for the extremely hard, latency-insensitive cases that actually need it.

Prompting implication

At high and above, you're paying for deliberation — so give the model something worth deliberating on. Put the full task spec up front, leave a large max_tokens so it has room to think and act, and define "done" so the thinking terminates on a target instead of wandering. A high-effort run against a thin prompt is deliberation you paid for and can't use.

Check yourself

When is max effort the right choice?

Before shipping a skill, how should you settle on an effort level?

Do it once

A Uniblock skill drives Claude Code to add a new chain across the unified-request codebase: edit constants, wire the provider, regenerate the OpenAPI schema, update CU mappings, run the type-checker. It's multi-step and agentic, it runs many times a week, and mistakes surface in tests and review. Pick an effort level for this skill's runs and justify it in two sentences. Then say what you'd do differently if this were instead a one-off, correctness-critical billing migration you only run once.

Model answer

Skill runs: xhigh (Claude Code's default), then sweep. It's routine agentic work where higher effort up front tends to reduce turn count — deeper first-pass thinking means fewer botched edits and re-runs, so the whole chain finishes cheaper. I'd sweep medium / high / xhigh against a couple of real chain-add runs and keep whichever tier lands the change correctly in the fewest turns; max is unjustified here because the task isn't especially hard and I run it constantly.

One-off billing migration: max. Now correctness clearly outweighs cost, it runs once, and I don't care about latency — exactly what max is for. I'd pair it with a full spec up front, a large max_tokens, and an explicit "done" definition so the deliberation has a target and I actually get value from the tokens I'm paying for.
