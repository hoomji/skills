Prompting · Lesson 7 · Orchestration

ultracode — orchestrating many agents

Effort makes one mind think harder; ultracode makes many minds think at once — and check each other.

The one win You know when to escalate from a single hard-thinking agent to a verifying swarm — and, just as important, when that swarm is overkill.

From depth to breadth

Lesson 6 gave you one dial: effort. Effort spends compute down — deeper reasoning inside a single context, one agent thinking harder per step before it answers. It is the right dial when the hard part is getting one chain of reasoning right.

But some tasks are not deep, they are wide. Auditing every provider adapter in unified-request for a missed rate-limit case. Migrating a convention across forty files. Answering a question where you would only trust the result if three independent readers agreed. No amount of single-context thinking fits that in one head — the work is larger than one context window, and one perspective cannot audit itself.

ultracode is the opt-in mode for exactly this. When it is on, Claude Code stops answering substantive tasks solo and instead authors and runs a workflow by default — spending compute across many independent processes rather than down through one.

What a workflow actually is

A workflow is not "an agent that decides to spawn helpers." It is a deterministic orchestration script: the control flow — the loops, the conditionals, the fan-out — lives in code, not in a model's moment-to-moment choices. That script fans out many subagents — in parallel (a barrier that waits for every result before the next phase) or in a pipeline (the default: each item flows through the stages independently, no barrier) — and synthesizes their results. On top of those primitives sit the quality patterns — the part a single agent cannot do for itself:

  • Adversarial verify — spawn N independent skeptics, each prompted to refute a finding. Keep the finding only if it survives.
  • Judge panel — generate N independent attempts, score them, synthesize the answer from the winner.
  • Loop-until-dry — keep discovering until K rounds in a row turn up nothing new.
  • Completeness critic — a final agent whose only job is to ask "what is missing?"

The three reasons it beats one agent

ReasonWhat it buys you
ComprehensivenessDecompose the task and cover the pieces in parallel — nothing falls off the end of one context.
ConfidenceIndependent perspectives plus adversarial checks before committing — a single context cannot audit its own blind spots.
ScaleTake on work larger than one context window can hold — migrations, audits, broad sweeps.

Note that only confidence is about being right on a narrow point; the other two are about size. That is the tell for whether breadth is what you actually need.

How to invoke it

ultracode is opt-in — it is not on by default. You turn it on by including the keyword ultracode, through a session setting or skill, or simply by asking for a workflow / multi-agent orchestration in your own words ("fan this out," "audit every adapter in parallel and cross-check the findings"). Trivial and conversational turns are still handled solo even when the mode is on — the harness does not waste a swarm on a one-liner.

Don't swing this at small nails A workflow can spawn dozens of agents and spend a large amount of tokens. Per the Workflow tool contract, concurrency is capped — only about a dozen agents run at once — and a workflow runs in the background, notifying you when it finishes. That cost is exactly why it is opt-in. A rename, a single-file edit, a "what's the flag for X" — those want a solo answer or, at most, max effort. Reach for ultracode only when the scale of the task justifies the scale of the spend.

The prompting implication

Here is the through-line from Lesson 6: escalating to a swarm does not lower the bar on your prompt — it raises the stakes on it. Max effort demanded a clear task spec and a definition of "done." A workflow demands the same discipline, because you are now spending that compute in parallel across many agents. A vague task fans out into a dozen vaguely-wrong answers, verified against nothing.

Under-posed

"ultracode: look over the codebase and find problems."

No scope, no bar. Twelve agents, twelve definitions of "problem," nothing to verify against.

Well-posed

"ultracode: audit every provider adapter for unhandled 429s. For each hit, spawn skeptics to refute it; report only survivors, with file and line."

Clear unit of work, clear verification bar, clear shape of "done."

So the two dials share one operating principle: effort dials depth, ultracode dials breadth — and both spend compute for correctness on hard work, and both waste it on easy work. The harness only amplifies a well-posed task. Pose it well.

Check yourself

When is spinning up an ultracode workflow the right call?

What does a workflow add that one max-effort agent cannot?

Do it once

Take this real task: "Uniblock is adding a new chain, and I want to confirm every JSON-RPC method we advertise for it is actually wired end-to-end — constants, schema, CU mapping, and adapter — with no gaps."

Decide: solo, max-effort-solo, or a workflow? If a workflow, sketch its shape — the phases, and exactly where verification goes. Write your answer before revealing.

Model answer

Call: a workflow. This is a breadth problem — many methods × four layers each — and it is exactly the kind of coverage claim you would only trust if it were independently checked. Depth alone (max effort, one context) would run out of room and could not audit its own misses.

Shape:

  1. Enumerate (parallel): one pass lists every advertised method for the new chain from the schema — the authoritative unit of work.
  2. Trace (pipeline): each method flows independently through a checker that confirms it appears in constants.ts, the OpenAPI schema, the CU mapping, and a live adapter. One item = one method's full trace.
  3. Adversarial verify: for every "wired correctly" claim, spawn skeptics prompted to refute it (find the missing layer). Keep the claim only if it survives.
  4. Completeness critic: a final agent asks "which methods, layers, or edge cases did we never touch?" — catching gaps in the enumeration itself.

Verification lives in steps 3 and 4 — after generation, run by agents who did not do the tracing. That separation is the whole point.
