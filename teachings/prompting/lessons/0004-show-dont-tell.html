Prompting · Lesson 4 · Few-shot examples

Show, don't tell

One good example steers harder than a paragraph describing what you want.

You've spent three lessons getting the words right — explicit, intentful, well-aimed, at the right altitude. This lesson adds a different instrument entirely: instead of describing the output you want, demonstrate it. For anything with a specific shape — a format, a tone, an edge-case rule — a couple of worked examples pin it down far more reliably than prose. This is the highest-leverage move for the skills you author.

The one win You'll replace vague style instructions ("keep it concise and consistent") with examples that make the model produce exactly the shape you want — and you'll know why your examples sometimes teach the wrong thing.

Move 1 — Demonstrate the shape instead of describing it

Some things are hard to say and easy to show. The exact structure of a commit message, the voice of a wiki summary, how terse a status line should be — you can burn a paragraph trying to specify it, or you can show one instance and let the model match it. Few-shot (a.k.a. multishot) prompting is just that: include input→output examples of the task before the real one.

Tell

"Summarize each source in a consistent, scannable style — lead with the decision, keep it tight, use our house voice."

Show

"Summarize like these:
— Decided: drop Redis, use Postgres LISTEN/NOTIFY. Cheaper to operate; team already knows PG.
— Decided: cassettes move to S3. Local disk was flaking CI on parallel runs.
Now summarize this: […]"

The "house voice" was three adjectives in the tell version and completely unambiguous in the show version — because the model can see it. This is the same instinct as Lesson 3's altitude: an example lets you delete a stack of prescriptive rules. Showing is often lower-noise than enumerating.

Anthropic's own guidance Examples are described as the most reliable lever for format and style — and for steering behavior, positive examples of the thing you want beat telling the model what not to do. When you catch yourself writing "don't do X," consider showing an instance of the right thing instead.

Move 2 — Make examples representative — including the hard cases

Here's the mechanism you have to internalize: your examples become the pattern the model generalizes from. If every example is the easy, uniform case, the model learns to handle only the easy case and improvises on the rest. Cover the variety you actually care about — especially the edge case you'd otherwise write a rule for.

  • Diversity over quantity. Three examples spanning the real range beat six near-identical ones. Include the tricky input, the empty input, the one that should be rejected.
  • Identical structure. Keep the input→output framing the same across every example (same delimiters, same fields) so the pattern is unambiguous.
  • 3–5 is the usual sweet spot; go higher for genuinely varied tasks.

Move 3 — The example is the ceiling: watch the accidental patterns

The flip side of "the model copies your examples" is that it copies everything regular about them — including patterns you didn't intend. If all your examples happen to be one line, output stays one line. If they all open with "Sure!", so will the model. If they're all the happy path, edge cases fall apart.

The discipline Hold constant only what should be constant; vary what should vary. Before you ship examples, scan them for regularities you didn't mean to teach.

This is also the trap when few-shot "mysteriously" degrades a capable model: the examples quietly capped it. On Opus 4.8 and Fable — which plan well on their own — a few sharp, well-chosen examples help, but a pile of mediocre or over-uniform ones can pull quality down. Curate, don't accumulate.

Do it once

Convert this tell instruction into a show one. Include at least one edge case, keep the structure identical, and check for accidental patterns before you reveal.

"Write a skill instruction so Claude formats git commit messages
consistently across the repo."
Reveal one strong rewrite (compare the moves)

"Write commit messages as <type>: <imperative summary> (type ∈ feat / fix / chore / docs / refactor). Like these:

feat: add pagination to the quotes endpoint
fix: stop dropping the last page in paginate()
refactor: extract clampPage() from list.ts

# breaking change — add `!` and a body explaining the migration:
feat!: require api_key on all provider calls

Providers now reject unauthenticated requests; callers must pass api_key."

The moves: shows the shape instead of describing it (Move 1) · includes the edge case (breaking change) so the model learns the rule from an instance, not prose (Move 2) · the body appears only where it's load-bearing, so the model learns "body = breaking change," not "always add a body" — an intentional regularity (Move 3). The summaries are all lowercase, imperative, no trailing period: those are deliberate constants, and the model will correctly copy them. If you didn't want lowercase enforced, you'd vary it in the examples.

When telling is fine You don't need examples for everything. For a simple, unambiguous ask ("list the three largest files"), a plain instruction is faster and clearer. Reach for few-shot when the shape is hard to state, when consistency across many runs matters (skills!), or when a plain instruction keeps missing the same way.
