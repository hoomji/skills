Fable vs Opus

Which model to reach for — and why the same prompt should read differently on each.

This is the lesson you've been curious about since day one. It has two halves: a decision (when is Fable worth it over Opus 4.8?) and a prompting shift (how your prompt should change when you switch). The second half is the more useful one — and it's the culmination of Lesson 3: the stronger the model, the higher you fly. Fable is where you fly highest.

Grounding Everything below is drawn from Anthropic's own model guidance in the in-repo claude-api skill — not my memory. Model facts about current models change fast; when in doubt, ask me to pull the exact passage.

The decision: Opus 4.8 is the daily driver, Fable is the heavyweight

Opus 4.8 is the default — it's what your Claude Code sessions run on, it handles the overwhelming majority of real work, and it's cheaper and faster. Fable 5 is Anthropic's most capable widely-released model, but it is not the default upgrade: it costs roughly twice as much, individual turns can run for many minutes, and it carries caveats (see the table). You reach for it deliberately, for a specific kind of task.

When Fable earns its price The hardest reasoning, long-horizon autonomous runs (overnight refactors, end-to-end deliverables), and first-shot builds of well-specified complex systems — work that exceeds what Opus handles cleanly. If Opus already does the job, Fable is just a slower, pricier way to get the same answer.

How to prompt it High altitude + explicit triggers and autonomy grants. Even higher altitude; de-prescribe; goal + the why; set boundaries.
Gotchas Narrates a lot; sweep effort per task. Refuses cyber/bio-adjacent asks; needs 30-day data retention (no ZDR).

Note the two failure modes are opposite. That's the whole reason the same prompt shouldn't be identical on both.

The prompting shift: fly even higher for Fable

Lesson 3 said stronger models want higher altitude. Fable takes this to the limit: Anthropic's guidance is explicit that prompts written for older models are often too prescriptive and actively reduce Fable's output quality. Step-by-step choreography that helped a weaker model gets in Fable's way — its own planning is better than your enumerated steps.

Tuned for an older model

"Step 1: list the files. Step 2: parse each. Step 3: rewrite the path. Step 4: upload. Step 5: verify. Step 6: delete the old one. Do them one at a time and report after each."

Tuned for Fable

"Migrate the cassettes to the new S3 layout so CI reads only the new paths with zero regressions. Why: the old layout flakes on parallel runs. Work autonomously and in parallel where safe; keep a running note of what's migrated and anything that doesn't fit the pattern."

The Fable version does four things the guidance calls for: de-prescribes (goal, not six steps), gives the why (Fable connects intent to the work better than it infers it), grants autonomy + parallelism (it delegates to subagents well), and offers a memory surface (a running note it can write to). None of that would you bother adding for a weaker model.

Steer the opposite failure modes

Because they fail in opposite directions, the corrective clause you add differs:

Opus 4.8 under-reaches

Grant autonomy & triggers

It asks too much and won't reach for capabilities by default. Push it forward:

"For minor choices (naming, defaults), pick a reasonable option and note it rather than asking. Delegate to subagents when work fans out. Check your memory file before long tasks."

Fable over-reaches

Set boundaries & nudge to act

It takes adjacent actions and can over-plan. Fence it and unblock it:

"When I'm describing a problem rather than requesting a change, report your assessment and stop. When you have enough to act, act — don't re-survey options you've already weighed."

Don't send Fable into the wrong task Fable runs safety classifiers on incoming requests and will refuse cyber- and bio-adjacent work (even benign-adjacent — security tooling can trip a false positive), returning stop_reason: "refusal". It also can't run under zero-data-retention. For that kind of work, or for anything latency-sensitive and interactive, Opus 4.8 is the right call regardless of raw capability.

Do it once

You have an Opus-tuned prompt for a big, autonomous job. Adapt it for Fable: raise altitude, add the why, grant autonomy, set a boundary, and plan for a long turn. Then reveal.

Reveal one strong Fable rewrite (and how Opus would differ)

"Go through .claude/skills and bring every skill's prompts in line with current-model guidance — the goal is no forceful CRITICAL/ALWAYS/NEVER scaffolding, since it makes today's models over-trigger. Why: I want these skills to steer Opus and Fable reliably, and the loud phrasing is working against that. Work autonomously across the skills in parallel; keep a running note of what you changed and any judgment calls. Apply the rewrites directly — I'll review the diff at the end rather than approve each file. This is a long pass; report progress, not per-file questions."

The moves: altitude raised (goal, not open/read/list/suggest/wait) · the why added · autonomy + parallelism granted (Fable's strength; also cures Opus's ask-too-much habit) · a memory surface (running note) · a boundary on review (diff at the end) · long-turn framing (progress, not questions).

For Opus 4.8 you'd keep almost all of this — Opus under-reaches, so the autonomy grant and "don't ask per file" are if anything more important. The one thing you'd watch differently: Opus narrates more and asks more, so the "review the diff at the end" boundary does real work; Fable needs the "act, don't re-survey" nudge more than Opus does.
