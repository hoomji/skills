Prompting Cheat Sheet

The compressed essence. Every prompt answers: what, why, how much — and sometimes it's better to show than say.

Lesson 1 · WHAT

Explicitness

The model acts on what you wrote, not what you meant. Name the things you'd otherwise assume:

  • Scope — which file/PR/range; what not to touch
  • Format — size, shape, audience of the output
  • Constraints — no new deps, keep signatures, etc.
Lesson 1 + 2 · WHY

Intent → Decision frame

Say the goal and what you'll do with the answer. Lets the model generalize to cases you didn't spell out.

  • What's the choice you're making?
  • What counts as a win?
Lesson 2 · APERTURE

Don't lead the witness

Naming a solution up front makes a capable model defend it, not compare.

  • Ask for options first; your idea is one candidate
  • Demand a recommendation + the risk, not a pros/cons survey
Lesson 3 · HOW MUCH

Altitude

Constrain the outcome and load-bearing constraints; leave method to the model.

  • Volume ≠ clarity — delete CRITICAL/ALWAYS/NEVER
  • Say each thing once, plainly, with the why
  • Stronger model → fly higher
Lesson 4 · SHOW

Show, don't tell

For a format/tone/edge-rule, demonstrate it — one example beats a paragraph.

  • Examples become the pattern the model copies — include the hard cases, keep structure identical
  • It copies accidental regularities too — vary what should vary
  • Positive examples > telling it what not to do

Before → after, one line each

✗ "Clean up the error handling."
✓ "In session.ts only, replace bare catch{} with logged typed errors — don't touch other files or add deps."

✗ "If we built a dashboard, would it help?"
✓ "I'm deciding whether to build cassette tooling this sprint; a win is fewer CI flakes. Propose the 2–3 lightest options (incl. non-tool), recommend one, name its risk."

✗ "CRITICAL: You MUST ALWAYS write tests."
✓ "Write tests for new behavior — this ships from main, so untested code hits production. If something can't be tested, say why."

Model note (Opus 4.8 · Fable)

Current frontier models follow instructions literally and eagerly. Forceful caps and "if in doubt, do X" cause over-triggering, not reliability. Fable specifically degrades under over-prescription — prompt it at the goal-and-constraints level and trust its planning. Weaker/older models are the reverse: lower altitude, worked examples, more scaffolding. (Source: in-repo claude-api skill.)

Spending compute: depth vs breadth

Lesson 6 · DEPTH

Effort

How hard one agent thinks per step (low→…→max), one context.

  • Default high; xhigh for coding/agentic (Claude Code's default)
  • max = correctness > cost; watch overthinking / diminishing returns
  • Sweep, don't assume — the cost/quality curve isn't monotonic
Lesson 7 · BREADTH

ultracode

Many agents in parallel + independent verification; opt-in.

  • For comprehensiveness, confidence, scale beyond one context
  • Costs dozens of agents / many tokens — justify it; not for trivial work
  • Same discipline as max: full spec up front + a definition of "done"

Both spend compute for correctness on hard work — and both waste it on easy work. Depth is one mind thinking harder; breadth is many minds checking each other.

Prove a change helped — don't vibe it (Lesson 8)

Every move above is a change you make, and the model is stochastic — one nice run proves nothing. Measure:

  1. Define the bar first — what "good" means, written down before you touch anything.
  2. Build a tiny eval — 5–10 representative cases (include the hard ones), each with a checkable pass condition.
  3. Change one variable, run each case a few times, compare to the bar, keep or revert.
  4. Keep it as a regression suite — re-run when the prompt, skill, or model changes.

A tiny sharp eval beats a big vague one; a single passing run is not verification — consistency across runs is. This is how you run the effort sweep, refine a skill, or prove a CLAUDE.md change actually worked.

The 30-second pre-flight

Before you hit enter, check:

  • Did I name the scope and what not to touch?
  • Did I give the why / the decision I'm making?
  • Am I leading — should I ask for options and a recommendation instead?
  • Is the altitude right — precise on outcome, quiet on method, no shouting?
  • Is the shape hard to state? Show an example instead of describing it.
  • After I change it, will I measure it (tiny eval, one variable) or just eyeball one run?
